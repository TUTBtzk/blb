## 2. 根因：**末尾**的残行落在「上一屏后缀」里面

`overlap()` 的模型是固定的：把**上一屏的后缀**与**本屏的前缀**逐位置对齐
（`start = previous.size() - length`，`length` 从最大往下试）。这就要求上一屏末尾的每一行
都能在本屏开头找到对应行。

- 上边（本屏首行）的残行：只要跳过它重新对齐就行 —— 第四轮已经这么做了。
- **下边（上一屏末行）的残行**：它永远落在被比较的后缀里，任何 `length` 都绕不开它。
  它在本屏里的对应行出现在**中间**（不可能是本屏前缀），所以按标题匹配是唯一出路；
  而它恰恰**没有标题**（`titleCount=0`，RecyclerView 把被裁掉的标题移出了可见树，
  只剩居中的锁和勾选圈 → `childCount=2`），`sameContent()` 和 `placeholderPair()`
  （后者要求 `childCount <= 1`，只适配普通目录的 ListView 行）都匹配不上 → `overlap == 0`。
- 附带伤害：这一行还会被当成新行加进目录，于是出现「全部目录行=32、末行「」」和
  「合并目录第 32 行：没有 title 节点」——一行空标题污染整份目录。

## 3. 修复：抓住源头，在捕获时丢掉这种残行

`CatalogScanner.captureScreen()` 里，在算 `clippedEdge` 之前调用新的
`dropUnreadableEdgeFragments()`：

判据（刻意收得很紧，三条同时满足才丢）：

1. **读不到标题**（`!structureReadable()`：标题为空、或标题坐标零面积）；
2. **贴着列表视口的上边或下边**（`bounds[1] <= viewport[1]` 或 `bounds[3] >= viewport[3]`）——
   说明它是被视口裁出来的；
3. **比同屏任何一行完整行都矮** —— 说明它是被裁短的尾巴。

丢掉的只是「没有身份也没有状态」的残行，它滚过几屏之后一定会在屏幕中间完整出现
（重叠锚点要求 ≥2 行且位移一致，保证每隔几行就有一整屏覆盖），所以它不承载任何证据。
日志留一行：「屏边残行（读不到标题、只有 Npx）不算目录行，已跳过：…」。

同时**撤掉了第四轮那段只处理首行的补救逻辑**（`leadingClippedFragment` + 跳过重对齐 +
`merge` 的 `protectLeading`）—— 源头既然丢掉了残行，`joinScreen` 就回到原来的样子，
不留两套半重叠的规则。

**护栏没有放宽**：高度正常、只是读不出来的整行不满足第 3 条，仍然按原样报
「存在不能确认身份的目录行」并拦住整趟扫描（有反例测试钉住）。
