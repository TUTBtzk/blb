## 问题 1：点「同步目录」不进入扫描，弹窗说「同步目录还缺选择器：catalog_directory_ready、catalog_directory_list、catalog_picker_list」

弹窗来自 `ui/SubscriptionFragment.java:605`，判据是 `SelectorSet.load(ctx).missing(Keys.REQUIRED_FOR_CATALOG)`。

### 关键事实
**`app/src/main/assets/selectors.json` 第 175–183 行里这三个 key 是有的**（`catalog_directory_ready` / `catalog_directory_list` / `catalog_picker_list`，候选也不是空的）。所以这不是"忘了写"，是**运行时读不到那一份**。两个候选根因，先证伪再改：

- **根因 A（最可能）**：`auto/SelectorSet.java:42-57` 的 `load()` —— **只要 `filesDir/selectors.json` 存在，就整份取代 assets，不做任何合并**。而设置页有「导出选择器」（`ui/SettingsFragment.exportSelectors()/doExport()`）会把 assets 复制成那份可热改的副本。用户以前导出过，那份副本是**加这三个 key 之前**的 → 新 key 在他手机上永远看不到。**这是设计缺陷，不是一次性事故**：以后每次往 assets 加 key 都会复发。
- **根因 B**：装到手机上的那个 APK 是更早构建的，assets 里还没有这三个 key。

### 先取证（两条，都要做，把输出贴进报告）
1. 本地：`unzip -p <构建出来的 app-debug.apk> assets/selectors.json | grep -c 'catalog_directory\|catalog_picker'` —— 证明 APK 里到底有没有。
2. 设备：让用户打开**设置页 → 选择器自检**，把对话框第一行「来源：…」原样发回来。显示 `assets/selectors.json` 就是根因 B；显示 `/data/user/0/com.example.blb/files/selectors.json` 就是根因 A。

### 要改的（两个根因都要堵，别只堵一个）
1. **`SelectorSet.load()` 改成合并**：先读 assets 打底，再用 `filesDir/selectors.json` **按 key 覆盖**（同 key 用副本的候选列表，副本没有的 key 保留 assets 的）。`source()` 要能说清「哪些 key 被本地副本覆盖了」。
2. **设置页加一颗「删除本地选择器副本（恢复内置）」**（带二次确认），并在自检对话框里列出被本地覆盖的 key。用户手指不灵便，这个按钮必须一眼能找到。
3. **缺 key 的报错要能自救**，现在的「请到设置页补齐后再同步」等于没说。改成三段：缺哪些 key / **当前读的是哪一份文件** / 如果那是 filesDir 的副本，就去设置页点「删除本地选择器副本」。
4. **重建 APK 并验证**：把上面第 1 条 grep 的输出贴进报告；同时确认新 APK 装上去后（覆盖安装不清数据）能进扫描流程。

### 验收
- 设置页自检里「同步目录」这一组显示**全部已配**。
- 点「同步目录」能真正开始扫描（日志出现扫描相关行），不再弹缺选择器。
- 「核对订阅清单」那一组不受影响（它走 `REQUIRED_FOR_AUDIT`，日志里 7 个号是跑通了的）。

## 问题 2：「核对订阅清单」只跑完 7/8 个号，卡在 w9899

`运行日志.txt` 第 50–67 行是现场：

```
[3/8]核对w9899 …
w9899在《反派干部今天也在扮魔法少女》上：订阅清单说订了20章、账本记着0条付费记录—账本漏记了20章
（完整核对明细）
明细未完整：读到6条；已打开=true，从顶=true，到底=false，截断=false，未读全=1，列表项覆盖=6/15；读取途中列表总项数改变，不能拼接两份明细
…
w9899在《…》上：逐章明细没有完整读取的证据，这一次没能核对
```

用户猜测"w9899 订了 20 章，明细页有点长"——**基本正确，但真正的病根不是长度**。

### 根因（四条，逐个点名）
1. `auto/SubscribedDetail.java:1189-1220` 的 `frameCoverage()` 拿 **`AccessibilityNodeInfo.CollectionInfo.getRowCount()` 当「列表总项数」**。这一页是懒加载的，这个数**会随滚动变大**（日志里先读到 15）。
2. `collectWithEvidence()` 第 **1068-1071** 行：项数与上一屏不同就**直接放弃**（"读取途中列表总项数改变，不能拼接两份明细"）。20 章的长列表**必然踩中** —— 短列表（5～7 章）碰巧一直不变，所以另外 7 个号都过了。
3. `ReadResult.complete()`（第 **105-113** 行）要求 `coveredItems == collectionItems` 且 `unreadableRows == 0`，也就是**逐个列表项位置全覆盖**。日期分组行、被屏边裁掉一角的行都会让它永远不成立。
4. "到底"只可能由第 **1093-1097** 行的覆盖成功分支给出；而真正滚不动时（第 **1101-1103** 行）反而返回 `reachedEnd=false`（"滚动请求失败，不能据此确认到底"）。**滚不动正是列表到底的正常表现，却被当成"不能确认"。**
5. 结果：`auto/SubscriptionAuditPolicy.bookBlocker()` 因为 1 个号拿不到凭证 → **整本书禁止购买**（日志开头："核对7/8个号，补记16，修正0，存疑0，未核对1"）。

### 要改的
1. **主判据换成聚合行互证**：把聚合行的章数 `VoucherLedger.Reading.chapters` 作为 `expected` 传进 `SubscribedDetail.read(...)`。`complete()` 改成：
   - 从列表第 1 项开始；
   - 已确认到底；
   - 每条都能读出身份（印刷章号，或「卷名 + 完整标题」经目录唯一映射），且金额、币种、日期都读得到；
   - 同一条反复出现时去重后**事实完全一致**（金额/日期/标题冲突就不算完整）；
   - **去重后的条数 == expected**。
   这一条最稳：expected 来自服务器的按书汇总，不吃 UI 懒加载的亏。
2. **列表项数降级为线索**：允许它在读取过程中变大（懒加载），取最新值记进日志即可；**绝不允许**因为"项数变了"把这一趟作废；最终与 expected 不一致时也只写日志，不阻断。
3. **到底的判定**：`scrollForward()` 返回 false（滚不动）**就算到底**；或当前屏出现最后一项；或已读条数已达 expected。三者任一成立即可。
4. **装饰行显式排除**：日期分组行（截图里的 "2026-09-08"）、页脚「清单约5分钟更新一次，可下拉刷新」、加载中提示，都不算交易行、也不计入"未读全"。只有"看起来是交易行但身份/金额/日期读不全"或"两次读到冲突事实"才计入 `unreadableRows`。判据写进注释。
5. **读不完整就重试一次**：退出明细页 → 重新点清单里那一整行 → 重读一遍。两遍都不完整才记未核实，日志把两遍的原因都写出来。
6. **日志要能自证**：写出「本次读到 N 条 / 聚合说 M 章 / 未读全的行原文（最多 3 条）/ 停在第几屏」。现在只有 "6/15" 这种数字，用户看不懂，也没法判断该不该人工介入。
7. **顺手修一个会误导人的日志**（我在日志里发现的）：明细页的印刷章号是**卷内号**，账本用的**全书位置号**，两者不是一回事。日志里"明细：第7章「寻找」"最后补成了"第100章"、"明细：第6章「薯片」"对应"第82章"，用户看到会以为补错了。要求：每一条明细日志都打全 **「卷名 + 印刷章号 + 全书章号 + 标题 + 金额」**；映射不唯一时**不许补记**（保持现状）。
8. **兜底开关（默认关，设置页）**：当某个号两遍都读不完整，而**聚合章数 == 该号账本付费条数 且 火券为 0**，允许签一份「聚合级凭证」，让它不卡住整本书；数量不等时**仍然阻断**。理由与残余风险（数量相同但记错了号，可能漏订一章）写进注释。默认关，因为 fail-closed 仍是默认姿势。

### 验收
- 真机重跑「核对订阅清单」：**8/8 全部核对完**；w9899 读到 20 条、补记 20 条。
- 日志里每一章都能一眼看出「卷内号 → 全书号」的对应关系。
- 跑完之后「跑今天的整套流程」不再因为"还有号未核实"而整本停。
- 单测覆盖：`complete()` 的新判据（条数==expected、冲突事实、缺金额、装饰行不计数）；行数在读取途中变大的用例（模拟 15 → 20）必须**通过**而不是作废。
