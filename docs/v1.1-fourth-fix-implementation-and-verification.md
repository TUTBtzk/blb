## 2. 根因

选择章节页是 `RecyclerView`（`downloadRecycler`），行高与普通目录一样是 138px。
短滑之后，最上面那一行被列表视口裁掉，只剩一条 34px 的尾巴（`232..266`），
而**它的标题 TextView 已经不在可见的无障碍树里** —— 剩下的是垂直居中、仍在可见带内的锁和勾选圈，
所以 `childCount=2` 而 `titleCount=0`、`title=""`。

拼接两屏时：

- `overlap()` 只按「上一屏的后缀 ↔ 这一屏的前缀」**逐位置**比对，而这一屏的第 0 行是空的，
  于是每一档长度都在第 0 行上对不上；
- 本来为这种情况准备的占位判据 `placeholderPair()` 要求 `childCount <= 1`（普通目录的
  `list_view` 行只有一个 title 子节点），而选择章节页的行有 2~3 个子节点（锁／标题／勾选圈），
  所以占位也匹配不上；
- 结果 `overlap == 0` → `gapNote` → 整趟不写账本。

也就是说：**普通目录页（ListView）靠占位判据能跳过这种残行，选择章节页（RecyclerView）不能。**
一行残行就把整趟同步废掉了。

## 3. 修复（`CatalogScanner.java`）

1. 新增 `leadingClippedFragment(rows)`：本屏首行同时满足
   - 结构读不全（`!structureReadable()`，标题读不到或没有面积）；
   - 行框贴着列表视口上边（`bounds[1] <= viewport[1]`）；
   - **比同屏任何一个读全的行都矮**（确认是被裁短的尾巴，而不是一行高度正常、只是读不出来）
2. `joinScreen()` 在 `overlap == 0` 时：跳过最多 `FRAGMENT_LIMIT = 3` 行这样的残行重新对齐；
   一旦找到 `>= 2` 个锚点的重叠区，就按「残行＝重叠区前一行」把位置对上并继续。
   几何上这是必然的：屏幕上紧挨在重叠区第一行上面的那一行，就是目录里排它前面的那一行。
3. `merge(..., int protectLeading)`：残行**只对位置，不替换**目录里那一行 ——
   它读不到标题，替换只会让这一章丢掉名字（它读到的锁／勾选状态本来也已经由那一行的完整快照表达）。
4. 日志留痕：「目录翻页首行是 N 行屏边残行（读不到标题），按重叠区前一行对位后继续：残行属于「X」等已读到的整行」。

**护栏没有放宽**：高度正常、只是读不出来的行不在这条豁免里，仍然按原样拦住整趟扫描
（新增反例测试钉住）。

## 6. 仍然未验证的事（本轮没有真机证据）

- **选择章节页能否真的扫到底**：RecyclerView 的正向容器探测到末页是否返回「拒绝」，
  只有明细页有真机证据（明细页也是 RecyclerView，一直正常）。若选择章节页的
  `ACTION_SCROLL_FORWARD` 在末页仍返回「接受」，会停在「没有确认到底」——
  那时改用「末项已出现 + 连续两次内容不变」作为次强证据，但需要新的真机日志确认。

  v7 那趟（483 章、免费 64 章）说明免费行是有勾选圈的，本轮日志只读到 13 章，还看不出来。
  下一次的日志里若有「目录「X」整行未读完整」，就按这条处理。
