## 步骤 1：订阅不再"订 1–2 章就换号"

### 现场与根因

用户原话：「有时只订阅 1 章就切换账号了。有时订阅了 2 章就切换账号（仍有余额）。
修改成优先消费当前账号，直到显示余额不足再切换账号。」

`SubscribeRun.runAccount()` 在**进选择章节页之前**自己算了一次「还买得起吗」：

```java
int estimate = lastPaid > 0 ? lastPaid : chapter.priceCoupons;   // 旧代码
String stop = stopBecauseBroke(name, budget, estimate, spentToday, plan.cap, chapter.chapterNo);
```

- `lastPaid` 是**上一章的实付价**（`SubscribeRun.java:307` 只在买成后更新），于是拿它当
  这一章的估价；真机账本里每章单价并不相同（10/11/12/14 代券），余额落在
  「下一章真价 ≤ 余额 < 上一章价」时就被判**买不起**、直接换号 —— 正是「有时 1 章、
  有时 2 章、余额还剩着」的形状。下一章是免费章时也照样白拦。
- `chapter.priceCoupons` 也不能当价：它是旧版按火券登记的历史遗留，扫目录只会写 -1。
- 用户在设置里的「每账号每日花费上限」是 **0（不限）**，所以每日上限不是本次的原因
  （代码里也已确认：`Prefs.dailySpendCap` 默认 0）。

### 改法

| 文件 | 改动 |
| --- | --- |
| `SubscribeRun.java` | 删掉进页前的估价拦截：`stopBecauseBroke(name, spentToday, cap)` 只保留一件**确定的事实** —— 账本里这个号今天已经花掉多少、是否已到每日上限。买不买得起交给页面回答。同时删掉 `lastPaid` / `budget` 两个只为估价存在的变量。 |
| `SubscribeRun.java` | `INSUFFICIENT` 如实报告：以前不管哪种「买不成」都写成「代券不够（页面上说余额不足）」，把「这一章只能花火券买」也混进去；现在写成「买不起这一章：<页面/实付的原文>」。 |
| `SubscribeRun.java` | 类注释与 `Plan.describe()` 同步改成「订到**页面显示余额不足**再换下一个号」。 |

**行为不变的部分**：买不起的章不标记已处理 → 下一个号会再试同一章（8 个号拼一本的设计）；
`ChapterBuyGuardTest` 钉住的「页面出现余额不足那一屏」判据一个字没动。

### 测试

- `SubscribeBudgetTest`：删掉编码旧契约的 6 条（`oneVoucherShortSwitchesAccount` 等），
  新增 `thePageDecidesWhetherThisAccountIsBroke`（不猜价：53 券买 20 券、余额 0 都要进页面）
  与 `anExhaustedDailyCapStillStopsAccount`（每日上限仍然是硬事实）。
- `SubscribeTaskTest.aRealPriceAboveTheRemainingDailyCapNeverClicksBuy`：改成断言
  「今天才花 5 券、没到上限 → 进页面」，真实的越界仍由付款门槛按页面实付拦住。
- `RunReportTest.beingStuckOnMoneyIsReportedButIsNotAFailure`：换上新的真实措辞。

## 步骤 2：账号页每行「切换账号」

- 新增 `ui/AccountSwitchAction.java`：把「切号守卫＋提示」抽成一份共用实现 ——
  无障碍开关（关着先尝试恢复）、有任务在跑、发起 `AutomationService.startSwitchAccount`。
  `DetailActivity.switchToBuyer` 改为调用它，两处判据不会再漂移。
- `AccountsFragment`：每行那个一直空着的 badge 槽改成**「切换账号」按钮**（15sp、48dp 高、
  contentDescription「切换账号：<备注名>」），点击 → **确认弹窗**（写明会退登再登、切号最容易
  触发验证码）→ 真正切号。行的点击（编辑）与长按（删除）不受影响。
- 新增 strings：`account_switch`、`account_switch_confirm_title`、`account_switch_confirm_message`。

## 步骤 3：「核对记录与存疑」页的「清理」

- `AuditDao.deleteLedgerAuditsOfNovel(novelId)`：`DELETE FROM ledger_audit WHERE novel_id = ?`
  —— 只清当前这本书（页面本来也只显示这一本），绝不碰 `purchase` / `chapter` / `novel` /
  `check_in_log` / `account_novel_audit`（购买闸门与核对进度在后者）。
- `activity_detail.xml` 头部新增 `detail_clear`（仿「导出」，默认 gone）；
  `DetailActivity.showSuspect()` 里显示并接上 `confirmClearAudits()`：
  目标书/空列表/忙碌三种情况先给明确提示，然后弹窗确认 —— **弹窗里写明会让「撤销」永久失效**
  （被修正或删除的订阅记录只活在那些留痕里）；确认后 `LedgerEdits.submit` 事务内删除，
  并清空订阅页那行「最后核对：…」摘要（`Prefs.setLastAuditSummary(id, "")`），
  最后 toast「已清理 N 条核对记录」。
- 新增 strings：`detail_audit_clear` / `_title` / `_message` / `_cleared` / `_empty` / `_no_target` / `_busy`。
- 新增设备测试 `AuditDaoTest.clearingOneNovelRemovesOnlyItsOwnAuditTrail`：只清这本书、
  别的书的留痕还在、购买记录/章节/`ledger_marker`/核对进度一条不动、清第二遍返回 0。
  （Room 的 DAO 只能在真机/模拟器上跑：本环境 `compileDebugAndroidTestJavaWithJavac` 通过，
  真机命令 `.\gradlew.bat connectedDebugAndroidTest`。）

## 用户下次跑「跑今天的整套流程」时应看到

- 一个号会一直往下订，直到**页面上真的出现「余额不足，快去充值吧」**才换下一个号；
- 日志里「买不起」那句话会写清是页面说余额不足、还是这一章只能花火券买；
- 若某个号真的没钱了，report 里那一行会点出账号名与章节号。
