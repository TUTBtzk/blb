## 1. 同步目录：任何情况下都不再往上滑

### 1.1 现场

`blb-log目录` 里同一个循环重复了 122 次：

| 行 | 内容 |
| --- | --- |
| 10 | 进目录页时在已读章节：「首行『第89章 绽放』，末行『第8章 继续』」 |
| 12–13 | 点击 goto_top「回到顶部」 |
| 14 | 到顶了：「首行『铃兰花』，末行『第14章 发现』」 |
| 15 | **回顶反向短滑第 1 次后**：又回到「第89章 绽放…第8章 继续」 |
| 15–135 | 每滑一次就刷新一次、跳回已读章节，再一路滑到顶，再刷新……共 122 次 |
| 137 | 失败：`回顶点击=1，反向滑动=122，边界探测=0` |

`边界探测=0` 说明循环一次都没走到真正的边界判据：真正的边界证据（原生容器动作返回「拒绝滚动」）
一次也没被用过，全部时间花在向下的手势上。

### 1.2 根因

`CatalogScanner.toTop()` 原来用**向下的手势**（`StepRunner.scrollCatalogBackward()` →
`BlbAccessibilityService.swipeCatalogDown()`，手指从视口 32% 滑到 72%）把列表往回带。
普通目录页支持下拉刷新（明细页页脚也写着「可下拉刷新」），所以：

- 在列表顶部，这条手势 = 下拉刷新 → 页面重建 → 应用自动跳回已读章节；
- 代码看到「内容变了」，判定「还没到顶」→ 再滑一次 → 死循环。

明细页早就有同样的教训（`SubscribedDetail` 的注释：**验顶不能派发下拉手势，只探原生反向动作**），
目录页当时漏了。

### 1.3 改动

| 文件 | 改动 |
| --- | --- |
| `CatalogScanner.java` | `toTop()` 的移动手段换成容器原生反向动作 `probeCatalogContainerBackward()`：`UNAVAILABLE` 直接失败；`BLOCKED` + 连续两次内容不变 = 物理顶部（原判据不变）；容器动过列表却又不肯拒绝时，只再用应用自己的「回到顶部」按钮重试有限次，超限如实失败。日志改成「回顶反向动作第 N 次后」，确认时写明「全程未派发向下手势」。 |
| `StepRunner.java` | 删除 `scrollCatalogBackward()`、`scrollDetailBackward()`；`scrollDetail` 只保留下滑方向。向下的手势入口在类型上不存在。 |
| `BlbAccessibilityService.java` | 删除 `swipeCatalogDown()`，`swipeCatalog` 只保留下滑方向。 |

### 1.4 顶部证据

- **强证据**：容器原生反向动作返回「拒绝」＋连续两次内容不变（和以前一样强，且不产生触摸事件，
  不会触发下拉刷新）。在顶部时 `AbsListView` 的 `ACTION_SCROLL_BACKWARD` 因为 `mFirstPosition == 0`
  返回 false；不在顶部时它会真的把列表往回带一屏（安全，无手势）。
- **弱证据**（只在容器动作对这个列表完全没有信号时启用）：`回到顶部`按钮**确实按下去过**
  （press 成功）**且按下去之后页面真的换了一屏**（现场第 14 行就是这样），之后连续两次内容不变。
  三个条件缺一个都不用 —— 例如「按了没反应」或「按钮都没按到」时仍然如实失败，
  不允许拿「暂时不动」冒充顶部。
- 两条证据都没有 → 失败且**不写账本**；即便误判，`CatalogSync.directoryMismatch`
  还会把普通目录与选择章节页逐行对照，行数不一致一样拦下来。

## 2. 核对订阅清单：w9899 这类长明细读得完

### 2.1 现场

`blb-log-2026-09-15..txt`：w9899 的明细页有 `CollectionInfo.rowCount=20`（7 个日期组头不计入项数），
两次尝试都失败：

| 行 | 内容 |
| --- | --- |
| 258 | 第 1 次：**20 条全读到、到底=true**，但 `未读全=2，列表项覆盖=18/20` → 判「明细未完整」 |
| 190 / 208 | 两个未分类项是当时的**第 8 项、第 12 项**：都是可见窗口的第一项、`@232`（正好是列表顶边），只读得到「」或「代券」 |
| 338 | 第 2 次：只读了 3 屏 10 条就退出，原因是「滚动后画面尚未稳定」 |
| 355 | 结论：w9899「本账号保持未核实」，其余 7 个号都核对成功 |

### 2.2 根因

1. `whole = inside(item, list)` 用 `boundsInScreen` 判断「整行可见」。真机上被视口裁掉的行，
   bounds 会被**夹**到列表边界上，于是行框顶边正好等于列表顶边、`inside` 判成 true、
   `whole=true`。代码把它当成「整行看得见却读不出来」，按 `SubscribedDetail` 1447-1458 行
   把该项**从 `covered` 里删掉**并记成未读全 —— 而同一项在别的屏早已完整读到
   （第 8 项在第 2 屏、第 12 项在第 3 屏都读过）。
   1453-1454 行的注释本来就写着「**仅屏边裁剪仍可保留此前完整观察**」，是 `whole` 算错了。
2. `mergeItemEvidence` 在「已知交易 → 未知」时会置 `unknownDate=true`，被裁的那一次观察
   顺手截断日期链（第 3 屏第 87 章当时就丢了组头日期）。
3. 未读全清单是**覆盖度更新之前**的快照，已经补齐的项还会留在最后的报告里（第 258 行
   「列表第 12 项」就是这种旧账）。
4. 一屏在 2 秒内没稳定就作废整轮（第 2 次只读到 3 屏 10 条）。

### 2.3 改动（`SubscribedDetail.java`）

| 改动 | 说明 |
| --- | --- |
| `clipped` 标记 | `ItemEvidence` 新增 `clipped`：未分类且**行框贴着列表视口上下边**（`clippedAtViewportEdge`）或本来就 `!whole`。零面积标题（懒加载）**不算**屏边裁剪，那条老护栏不动。 |
| 覆盖证据 | `clipped` 的一次观察什么都不改：不删 `covered`、不记未读全（它只是这一屏没看全，滚到中间就能读）。 |
| 日期链 | `mergeItemEvidence` 遇到 `clipped` 的重复观察直接 `continue`，不污染已有身份与日期。 |
| 问题清单 | `problems` 在覆盖度更新**之后**重算，补齐的项不再留旧账。 |
| 稳定性 | 一屏没稳定不再作废整轮：首屏与「已不在明细页」仍然当场停；其余先原地重读最多 2 次，仍不稳定就往前翻一屏继续读，连续 3 屏不稳定才失败。漏读最后由「列表项覆盖」在结尾拦住。 |

按第 1 次尝试的数据推演：两个未分类项都变成「屏边裁剪」→ `covered=20/20`、`未读全=0`、
`到底=true`、`entries.size()==20==聚合章数` → `SubscriptionAuditPolicy.detailProblem` 返回 null
→ 走 `RemoteLedgerRecovery` 把「清单说 20 章、账本 0 条」补进账本并签发凭证。

### 3.2 真机验收清单（下一位执行者按顺序核对）

1. 从阅读中段进入普通目录并点「同步目录」，导出运行日志：

### 3.3 已知未验证项

- 真机 `android.widget.ListView` 的 `ACTION_SCROLL_BACKWARD` 是否返回「拒绝」：日志里从没走到过
  （`边界探测=0`）。AOSP 的 `AbsListView` 在 `mFirstPosition == 0` 时返回 false，
  但本机没有直接证据；弱证据路径就是为这种情况准备的，**它不会放开护栏**（见 1.4）。

  真机上应表现为日志里出现「明细第 N 屏未稳定，原地重读第 1 次」或「这一屏不算证据，继续往下读」。
