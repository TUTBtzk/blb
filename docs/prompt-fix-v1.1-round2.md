## 1. 问题 1：「同步目录」在普通目录页回顶时中止，什么都没扫到

### 1.1 运行日志（截图①）

结论行：`同步目录未完成：回顶途中目录不稳定：目录标题或整行标记没有读完整，无法确认章节顺序`。

### 1.2 「目录列表」页长什么样（截图③，逐项抄给你）

### 1.5 这份快照**还缺**什么（用户会补，你不要猜）

### 1.6 代码路径
`auto/CatalogSync.java:100-116`：`openCatalogDirectory()` → **`CatalogScanner.toTop(r, null, 120)`** → `scanDirectory()` → `openChapterPicker()` → `toTop()` → `scan(r, directory)`。这次死在**第一个 `toTop`**：`auto/CatalogScanner.java:836-838`。

### 1.7 根因（五条）
**R0 本地选择器副本整份盖住 assets。** `auto/SelectorSet.java:42-57`：只要 `filesDir/selectors.json` 存在就**完全取代** assets，不做合并；而设置页有「导出选择器」会生成这份副本（快照里那行 `选择器来源=` 已经证实用户手机上就有）。**后果：本轮无论往 `assets/selectors.json` 里加什么新 key（包括 R1 要加的目录页回顶按钮），用户手机上都不会生效**，只会再弹一次"缺选择器"。

**R1「回到顶部」认错了按钮。** `Keys.CHAPTER_LIST_TOP` 只配了 `{"id": "goto_top"}`，那是**选择章节页**右下角那颗；普通目录页的回顶是**叠在列表上的浮动圆形向上箭头**。`toTop()` 第 812-813 行在目录页找不到它，只能靠反向滚，而反向滚每一步都要过 R2 那道闸门。

**R2「屏幕稳定」和「每行都读全」被绑成一个判据。** `settledScreen()`（`CatalogScanner.java:542-563`）要求 `screen.complete` 才算一次"相同"；`Screen.complete`（第 410-422 行）要求**每一行**都 `complete()`（第 373 行＝`structureReadable() && stateKnown()`，屏边行只在 `structureReadable()` 时才豁免）。目录页是滚动/懒加载页面，只要有一行不完整，整屏就永远"不稳定"。

**R3 目录页确实存在"读不全"的行，来源有二，都还没被证伪。**
  a. `captureScreen`（第 445-472 行）在目录模式下**直接遍历 ListView 的每一个 child**。卷标题行「铃兰花」「星彩」和「一卷总结」很可能**没有 id=title 的节点**（截图里它们没编号、没锁、样式不同），`title == null` → `structureReadable()=false`。
  b. **浮动箭头按钮如果也是 ListView 的 child（或叠在列表里的可点容器）**，同样会被当成一行，而它没有 title。
  另外，回顶途中抓到的**瞬时帧**（半行、懒加载未铺开）也会触发同一个判据。

**R4 不稳定就直接抛异常中止。** `toTop()` 第 836-838 行一遇 `!current.stable` 就 `throw new StepFailure(...)`。于是整趟**一个动作没做、一个数字都没有**，用户只看到一句没法下手的话。

### 1.8 要改的（按这个顺序）

**R0 先修选择器加载（硬前置，必须先做）**
- `SelectorSet.load()` 改成**合并**：assets 打底，`filesDir/selectors.json` **按 key 覆盖**（同 key 用副本的候选列表；副本没有的 key 用 assets 的）。`source()` 要说得清"哪些 key 来自本地副本"。
- 设置页加「删除本地选择器副本（恢复内置）」按钮（二次确认），自检对话框里列出被覆盖的 key。
- 缺 key 的提示改成可自救：缺哪些 / **当前读的是哪一份文件** / 若是本地副本就去点那颗删除按钮。
- **验收**：本地副本存在时，往 assets 新增一个 key，App 里也必须能命中它（要有单测或明确的验证步骤）。

**R1 回顶改用它，并且点了必须核对**
1. 给目录页的回顶按钮单独配一个 key（例如 `catalog_directory_top`）：首选 dump 里拿到的真实 id；`chapter_list_top` 保留原来的 `goto_top`（选择章节页仍要用）。
2. **没有 id 时的结构兜底**（写成纯函数 + 单测）：在整窗口树里找 **CLICKABLE、无 text/desc、bounds 近似正方形（宽高差 < 20%）**、并且**成对出现**（两颗尺寸相近、x 基本对齐、y 相邻）的节点；**y 较小的那颗是"向上"**。
3. **点完必须核对真的到顶**（安全线，不许省）：首次扫描要求「第一行是全书第一行」**且**「反向滚不动」；再次扫描要求能找回上次的首行。
4. 核对不过就：再点一次 → 不行退回一屏一屏反向滚 → 仍不行就**如实报**「点了回顶按钮 N 次、反向滚 M 次都没到顶，现在停在第 X 行附近（首行「…」）」。
5. **点错一颗的后果要拦住**：页面上有两对圆形箭头。如果点到的是"到底部"，扫描会从书尾开始、目录顺序整本反过来、账本章号全错。所以失败时要把**当前首行的文本**报出来，让人一眼看出是不是被送到了底部。

**R2 把「屏稳定」和「行读全」拆开**
- `stable` 改成：连续 3 次**签名相同**（沿用现有 signature），**不再要求每行 `complete`**。
- 行读不全 → 记进 `Result.unresolved`（字段已存在），**扫完再统一判定**：`unresolved` 非空 → 不写账本 + 如实报告"哪几行、缺什么"。
- **绝不允许在滚动/回顶过程中因为某一行不完整就抛异常中止**。只有"一行都读不到""找不到唯一纵向列表容器""页面已经不是目录页"这类**页面级**问题才中止。
- 自查：故意造一个满屏空标题/半行的页面，扫描要能走完并给出结论（哪怕是"没扫干净"）。

**R3 目录页的行分类按目录页自己的结构来**
- 按 dump 把 ListView 的 child 分成三类：**卷标题行**（进 `skipped`，**不许再要求它有 title 节点**）、**章节行**（第 1.4 节那种规整结构：可点 RelativeLayout + 唯一 `id=title`）、**无法判定的行**（进 `unresolved`，逐条带原文）。
- 「一卷总结」这种既无编号、又不像卷标题的行，落进 `unresolved` —— **报告出来让人看，绝不要猜**。
- 明确排除**浮动控件**：与 R1 认出来的那对圆形按钮 bounds 重合的 child 不算行。
- 卷标题行绝不能进 `chapters`（进了账本就会被当成可买的章）。

**R4 诊断信息必须够**（现在完全不够）
报错与日志要带：**哪一行**（原文，或"空标题/没有 title 节点/是浮动控件"）、**缺什么**（标题为空 / 行内有 2 个 title 节点 / 零坐标 / 屏边裁剪）、**当前屏行数与首末行文本**、**已滚动次数与进入时的大概位置**。`DirectoryRowEvidence` 里已有 viewId / className / childCount / directTitle / heading，直接打出来。

**R5 降级策略**
目录页扫不动时默认**不写账本**（章号错位比缺番外危险得多），但结论必须给出**可操作**的下一步；设置页加「目录页扫不动时，退化成只扫选择章节页（会缺番外）」开关，默认关。用户现在的处境是"点了没反应"，宁可给他一个带警告的降级选项。

**R6 单测**
R2/R3 的判据做成纯函数用例：空标题行、没有 title 节点的行、两个 title 节点的行、零坐标行、屏边半行、懒加载途中签名变化、"点错按钮导致首行是最后一章"的核对失败、**浮动控件被误当成行**。断言：`stable` 只由签名决定；异常行被收进 `skipped`/`unresolved` 而不是抛异常。

### 1.9 验收
- 真机点「同步目录」能一路跑完（普通目录 → 选择章节两页）；日志能看出：进入时的大概位置、回顶点了几次/点了哪颗、每页读到多少行、跳过了哪些卷标题、`unresolved` 是哪几行。
- 账本章数包含番外；结论里不再出现"回顶途中目录不稳定"这种没有下文的话。

## 2. 问题 2：「核对订阅清单」只跑完 7/8 个号，卡在 w9899

### 2.1 现场（`运行日志.txt` 第 50-67 行）
```
[3/8]核对w9899 …
w9899在《反派干部今天也在扮魔法少女》上：订阅清单说订了20章、账本记着0条付费记录—账本漏记了20章
（完整核对明细）
明细未完整：读到6条；已打开=true，从顶=true，到底=false，截断=false，未读全=1，列表项覆盖=6/15；读取途中列表总项数改变，不能拼接两份明细
…
w9899在《…》上：逐章明细没有完整读取的证据，这一次没能核对
```
结尾：「核对7/8个号，补记16，修正0，存疑0，未核对1」。截图②显示这一页 20 条、按日期分组、每屏约 6 条。

### 2.2 根因（五条）
1. `auto/SubscribedDetail.java:1189-1220` 的 `frameCoverage()` 拿 **`AccessibilityNodeInfo.CollectionInfo.getRowCount()` 当「列表总项数」**。这一页懒加载，这个数**会随滚动变大**（日志里先读到 15）。
2. `collectWithEvidence()` 第 **1068-1071** 行：项数与上一屏不同就**直接放弃**（"读取途中列表总项数改变，不能拼接两份明细"）。20 条的长列表**必然踩中**；3～7 条的短列表碰巧不变，所以另外 7 个号都过了。
3. `ReadResult.complete()`（第 **105-113** 行）要求 `coveredItems == collectionItems` 且 `unreadableRows == 0`，即**逐个列表项位置全覆盖**。日期分组行、屏边被裁的行都会让它永远不成立。
4. "到底"只能由第 **1093-1097** 行的覆盖成功分支给出；真正滚不动时（第 **1101-1103** 行）反而返回 `reachedEnd=false`（"滚动请求失败，不能据此确认到底"）。**滚不动正是到底的正常表现，却被当成"不能确认"。**
5. 后果被放大：`auto/SubscriptionAuditPolicy.bookBlocker()` 只要有一个启用账号拿不到凭证，就**禁止整本书购买**。

### 2.3 要改的
1. **主判据换成聚合行互证**：把聚合行章数 `VoucherLedger.Reading.chapters` 作为 `expected` 传进 `SubscribedDetail.read(...)`。`complete()` 改成：从第 1 项开始 ＋ 已确认到底 ＋ 每条身份/金额/币种/日期可读 ＋ 同一条反复出现时去重后事实完全一致 ＋ **去重后的条数 == expected**。expected 来自服务器按书汇总，不吃 UI 懒加载的亏。
2. **列表项数降级为线索**：允许它在读取中变大，取最新值写进日志；**绝不允许**因为"项数变了"作废；最终与 expected 不一致时也只写日志。
3. **到底的判定**：`scrollForward()` 返回 false（滚不动）就算到底；或当前屏出现最后一项；或已读条数已达 expected。三者任一成立即可。
4. **装饰行显式排除**：日期分组行（截图②里的 "2026-09-08"）、页脚「清单约5分钟更新一次，可下拉刷新」、加载中提示，都不算交易行、也不计入"未读全"。判定依据先 dump 确认再写进注释（别猜）。
5. **读不完整就重试一次**：退出明细页 → 重新点整行 → 重读一遍；两遍都不完整才记未核实，日志写清两遍原因。
6. **日志要能自证**：「本次读到 N 条 / 聚合说 M 章 / 未读全的行原文（最多 3 条）/ 停在第几屏」。现在只有 "6/15" 这种数字，用户看不懂。
7. **顺手修一个会误导人的日志**：明细页的印刷章号是**卷内号**，账本用的是**全书位置号**（日志里"明细：第7章「寻找」"被补成"第100章"、"明细：第6章「薯片」"对应"第82章"，用户会以为补错了）。每条明细日志打全 **「卷名 + 印刷章号 + 全书章号 + 标题 + 金额」**；映射不唯一时**不许补记**（保持现状）。
8. **兜底开关（默认关，设置页）**：某个号两遍都读不完整，而**聚合章数 == 该号账本付费条数 且 火券为 0** 时，允许签一份「聚合级凭证」不卡住整本书；数量不等时**仍然阻断**。残余风险（数量相同但记错了号，可能漏订一章）写进注释。

### 2.4 验收
- 真机重跑「核对订阅清单」：**8/8 全部核对完**；w9899 读到 20 条、补记 20 条。
- 日志里每一章都能一眼看出「卷内号 → 全书号」的对应关系。
- 跑完之后「跑今天的整套流程」不再因为"还有号未核实"而整本停。
- 单测：新 `complete()` 判据；**行数在读取途中变大（15 → 20）的用例必须通过而不是作废**。

## 4. 开始之前先回答我六个问题
